# HR-асистент: RAG по трудовому праву України та HR-політиках компанії + evals

ДЗ 2 курсу AI Engineering (robot_dreams), кейс блоку 2 «RAG на власних даних + Evals». Продовження HR-проєкту з [ДЗ 1](https://github.com/VelychkoDmitriy/structured-extraction): рекрутер чи HR питає («скільки триває випробувальний строк?», «чи можна звільнити працівника під час відпустки?», «скільки днів відпустки в senior developer?»), асистент відповідає лише за документами й цитує документ і розділ. Якщо в документах відповіді немає, каже про це.

**Результат (v5, 53 питання, з них 20 — holdout, якого система не бачила під час налаштування):**
- точність 1.00 (holdout — 20/20);
- «не знаю» на всі 9 питань без відповіді;
- faithfulness 0.955;
- кожна відповідь з посиланням на документ і розділ;
- **$0.30 за 1 000 питань.**

LLM-суддю відкалібровано на 15 ручних мітках: 80% згоди наосліп (суддя суворіший за людину, хибних «pass» 0), після розбору — 100%.

Пошук: hybrid + rerank + фільтр метаданих — MRR 0.95 проти 0.79 у vector-only. Метрики, порівняння версій і розбір помилок — **[REPORT.md](REPORT.md)**.

```bash
make run                  # або python main.py all: ingest -> index -> eval пошуку -> eval відповідей з порогами
python main.py ask "Скільки днів відпустки має Senior Developer?"
```

## Ingestion

```bash
python main.py ingest
```

[src/hr_rag/ingest.py](src/hr_rag/ingest.py): витягування → очищення → дедуплікація → chunking → метадані. Результат — у `data/processed/`:
- `chunks.jsonl`;
- `manifest.json` (статус, хеші, кількість чанків кожного документа, `dataset_version`);
- `audit.jsonl` (що сталося з кожним документом);
- `chunking_report.md`.

**Витягування — під кожне джерело:**
- **zakon.rada (версія для друку):** абзаци з `div#article`, «Розділ / Глава» → `##`, «Стаття N» → `###`. Конвенції МОП там — передформатований текст із жорсткими переносами: абзаци відновлюються за відступами.
- **Держпраці:** запитання-відповіді — вкладені акордеони (тема → питання → відповідь).
- **PDF:** layout-aware розбір (`pymupdf4llm`), тож заголовки й таблиці зберігаються. Таблиця, розірвана сторінкою, склеюється назад (друга частина не має заголовка, і парсер приймає перший рядок за заголовок). Скан без тексту позначається `ocr_required` і не індексується.
- **DOCX:** обхід у порядку документа, стилі → заголовки та нумерація, таблиці → рядки Markdown.
- **CSV:** таблиця з заголовком у кожному чанку.

**Очищення:**
- NFKC, невидимі символи;
- колонтитули (рядок, що є на більшості сторінок; рядки таблиць не чіпаємо) і «Page N of M»;
- переноси слів;
- редакційні примітки zakon.rada `{Із змінами, внесеними згідно із…}` і посилання-артефакти «( 2481-14 )»;
- розріджений заголовок PDF (межі слів втрачено) замінюється назвою документа з реєстру;
- маскування телефонів і e-mail.

**Дедуплікація:**
- точні копії документів — за content hash канонічної форми;
- майже-дублікати (Jaccard 5-шинглів ≥ 0.8) **не видаляються**: це версії, і `is_current` у метаданих каже, яка чинна;
- на рівні чанків — дослівно однакові чанки (стаття, що не змінилася з 2020 року) лишаються тільки в чинній редакції, тож у старій версії індексуються лише змінені статті.

**Метадані кожного чанка:**
- джерело (URL), назва, розділ («Глава III > Стаття 38»), `header` для contextual header;
- мова, тип документа (`law / ilo / guidance / company_policy / company_data`), формат;
- версія, `version_group`, `is_current`;
- хеш документа і чанка, кількість токенів, версія пайплайна.

## Chunking: чому так

Документи корпусу мають явну структуру: закон — розділ → глава → **стаття**, політика — розділи, FAQ — питання. Користувач питає саме про статтю чи розділ, і цитувати треба їх. Тому:

1. **Межа чанка — межа розділу або статті.** Стаття законодавства — це смислова одиниця, на яку посилаються («ст. 38 КЗпП»). Чанк, що містить кінець однієї статті й початок іншої, змішує дві норми, і модель може приписати одній статті правило з іншої.
2. **Усередині розділу — цілі абзаци до 450 токенів.** Більшість статей коротші (медіана ≈ 300 токенів), тож стаття = чанк. Довга стаття ріжеться між абзацами, потім між реченнями чи пунктами переліку «1) …; 2) …». Продовження зберігає заголовок статті.
3. **Таблиця ріжеться тільки між рядками**, із заголовком таблиці в кожній частині.
4. **Дрібні розділи** (< 40 токенів) і вступ документа зливаються з наступним розділом того ж батька.
5. **Contextual header** «Назва документа > Глава > Стаття» зберігається в `header` і додається до тексту під час embeddings.

Чому 450: модель embeddings (`multilingual-e5`, крок 2) читає 512 токенів свого токенізатора. Для українського тексту 450 токенів cl100k ≈ 400–480 токенів XLM-R, разом із contextual header це вміщується без обрізання. Чанк такого розміру вміщує одну статтю цілком: модель бачить норму разом із винятками, а не уривок.

**Порівняння з фіксованим вікном** (400 токенів, перекриття 60; повна таблиця по типах документів — `data/processed/chunking_report.md`):

| | структурний | фіксований 400/60 |
|---|---|---|
| чанків | 3 661 (до дедуплікації) | 3 029 |
| середній / макс. розмір, токенів | 305 / 675 | 398 / 401 |
| починається посеред речення | **6.2%** | 89.7% |
| два розділи (статті) в одному чанку | **0.6%** | 49.9% |
| чанк знає свій розділ (для цитати) | **99.3%** | 0% |
| розрізані рядки таблиць | 0% | 0.1% |

- **Посеред речення:** 6.2% у структурного — це продовження довгих переліків у статтях («інші права, встановлені законодавством;»), завжди з заголовком своєї статті.
- **Максимум 675:** заголовок-питання в FAQ Держпраці буває на 300+ токенів і повторюється в продовженні.
- **Фіксоване вікно:** кожен другий чанк змішує дві статті, і жоден не може назвати свій розділ. Відповідь «згідно зі статтею N» з таким чанком побудувати не можна.

Приклад — таблиця добових на двох сторінках PDF. Фіксоване вікно обриває її після рядка «Kyiv | 600 UAH | 2,500 UAH». Структурний чанк містить усю таблицю з одним заголовком, склеєну з двох сторінок (`data/processed/chunking_report.md`).

Вплив на пошук: MRR 0.794 (структурний) проти 0.785 (фіксований), vector-only, 15 питань. На пошук chunking майже не впливає. Різниця — у цитуванні: лише структурний чанк знає свою статтю.

## Пошук

[src/hr_rag/search.py](src/hr_rag/search.py): усе локально, без API.
- **embeddings** `intfloat/multilingual-e5-large` (fastembed, ONNX, CPU): українська й англійська в одному просторі, тож англійське питання знаходить українську статтю;
- **векторна БД** Qdrant (in-memory) з фільтрами за метаданими: `is_current`, `doc_type`, `lang`, `doc_id`;
- **BM25** за лемами (pymorphy3: «відпустки», «відпусткою» → «відпустка»);
- **hybrid** — Reciprocal Rank Fusion; **reranker** `BAAI/bge-reranker-v2-m3` по top-20;
- кеш embeddings за хешем тексту фрагмента: повторний запуск і CI нічого не перераховують.

| конфігурація (15 питань) | recall@1 | recall@5 | MRR@10 |
|---|---|---|---|
| фіксовані чанки, vector | 0.73 | 0.87 | 0.785 |
| vector | 0.67 | 0.93 | 0.794 |
| BM25 | 0.53 | 0.73 | 0.628 |
| hybrid (RRF) | 0.73 | 0.87 | 0.814 |
| hybrid + rerank | 0.80 | 0.93 | 0.878 |
| **hybrid + rerank + `is_current`** | **0.93** | **1.00** | **0.950** |

## Встановлення

Потрібен **Python 3.12+**: ТЗ вимагає 3.10+, а закріплена numpy 2.5 працює з 3.12 (pymupdf 2.1 і onnxruntime — з 3.11). Перевірено на 3.12.10, CI — 3.12.

```bash
python -m venv .venv
.venv\Scripts\activate          # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
copy .env.example .env          # Linux/macOS: cp .env.example .env, далі вписати OPENROUTER_API_KEY
```

Команди: `make run` (увесь пайплайн), `make check` (те, що запускає CI), `make ask Q="..."`, `make corpus` (перезавантажити корпус). На Windows без make — `python main.py all` тощо.

Без ключа працює все, що є в кеші (`set HR_RAG_OFFLINE=1`, як у CI). Ключ потрібен лише для нових питань і нових версій промпта. Перша побудова індексу завантажує моделі (~2.5 ГБ) і рахує embeddings ~85 хв на CPU; з кешем у репозиторії — секунди.
